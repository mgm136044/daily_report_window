# 설계 노트

[English](design.md) · [README](../README.ko.md)

이 도구가 왜 이런 모양인지에 대한 기록. 아래 수치는 전부 실제로 재서 얻은 것이다.

## 문제의 성격

코딩 에이전트는 이미 자기가 한 일을 상세히 기록한다. Claude Code 는 세션마다 JSONL 전사본을, Codex 는 스레드마다 하나를 남긴다. 둘 다 프롬프트, 모든 도구 호출, 건드린 모든 파일을 담는다. **기록은 이미 있다.** 다만 읽을 수 없을 뿐이다 — 수백 개 파일에 흩어져 있고, 다시 볼 일 없는 도구 출력 수백 MB 와 섞여 있다.

즉 이건 기록의 문제가 아니라 **압축과 귀속의 문제**다.

## 용량 — 원본은 안 들어가고, 쓸모 있는 부분은 들어간다

하루가 건드리는 전사본은 300~470 MB 다. 이 숫자 때문에 사람들은 청킹이나 임베딩, 계층 요약이 필요하다고 생각한다.

필요 없다. 그 용량의 대부분은 `tool_result` — 파일 덤프, 검색 출력, 명령 표준출력이다. 에이전트가 **본 것**이지 **한 것**이 아니다. 그걸 버리고 프롬프트·도구 입력·파일 변경 기록만 남기면 하루가 **30~180 KB**, 즉 8천~4만 5천 토큰이 된다. 단일 모델 호출에 여유 있게 들어간다.

나흘치 실측:

| 원본 후보 파일 | 추출 후 | 압축비 |
|---|---|---|
| 471 MB | 68 KB | 7,100× |
| 374 MB | 211 KB | 1,810× |
| 331 MB | 128 KB | 2,655× |
| 314 MB | 66 KB | 4,859× |

추출에 1초가 안 걸린다. 계층 요약은 하루가 안 들어가게 될 때 꺼낼 최적화이지, 처음부터 넣을 설계가 아니다.

## 시간 — 파일의 시각은 레코드의 시각이 아니다

세션 전사본은 그 세션이 재개될 때마다 이어 붙는다. 여기서 실측한 한 파일은 **34일**에 걸쳐 있었다. 수정 시각으로 파일을 고르고 그 내용을 "오늘" 로 취급하면 한 달치 무관한 작업이 딸려 들어온다.

레코드마다 자기 시각이 붙어 있으므로 **레코드 단위로 거른다.** 파일 수정 시각도 여전히 쓸모는 있다 — 창 이전에 마지막으로 손댄 파일은 창 안의 레코드를 가질 수 없으니, 후보를 줄이는 사전 필터로만 쓴다.

## 노이즈 — 셸 명령의 4분의 3은 탐색이다

실제 하루에 수집된 셸 명령 중 **74%** 가 `ls`·`cd`·`cat`·`grep`·`find` 부류다. 에이전트가 주변을 어떻게 둘러봤는지를 말할 뿐 무엇을 이뤘는지는 말하지 않으면서, 바이트 수는 지배한다. 이걸 걷어내고 거의 같은 명령을 중복 제거하면, 읽는 사람이 원할 만한 것을 하나도 잃지 않으면서 digest 가 절반이 된다.

## 귀속 — 작업 디렉터리는 프로젝트가 아니다

전사본은 레코드마다 `cwd` 를 기록하는데, 대개 프로젝트보다 몇 단계 아래다 — `…/v4/docs/04_보고서`, `…/assets/photos`. 하루 작업을 그런 이름으로 부르면 아무도 못 읽는 보고서가 나온다.

각 `cwd` 를 위로 걸어 올라가 프로젝트 마커(`.git`, `pyproject.toml`, `package.json`, `CONTEXT.md` 등)를 가진 가장 가까운 디렉터리에서 멈춘다. 설정된 컨테이너 디렉터리에서도 멈춘다. 두 규칙은 당해 보고서야 얻었다.

- **마커를 가진 컨테이너는 그래도 프로젝트다.** 이전 판은 그런 곳에서 돌아간 세션을 전부 버렸다.
- **컨테이너 자신은 절대 답이 아니다.** 그리고 이 검사가 "컨테이너의 자식은 프로젝트" 규칙보다 **먼저** 와야 한다. 안 그러면 `~/Downloads` 가 부모(`~`)가 컨테이너라는 이유만으로 자기 자신을 반환한다.

한글처럼 ASCII 가 아닌 폴더 이름에는 한 단계가 더 필요하다. macOS 는 파일시스템에서 경로 구성요소를 **자모분리(NFD)** 로 돌려주는데 세션 레코드는 **완성형(NFC)** 으로 갖고 있다. 화면에서는 똑같아 보이고 문자열로는 다르다. 그래서 같은 폴더가 영원히 합쳐지지 않는 두 프로젝트로 갈라진다. 수집 시점에 전부 NFC 로 통일한다.

## 포착 범위 — 에이전트는 자기가 건드린 것만 기록한다

두 에이전트 모두 **자기 파일 도구로** 편집한 파일만 기록한다. 에이전트가 대신 스크립트를 돌리면 — 빌드, 렌더러, 파일 마흔 개를 쓰는 heredoc — 로그에는 셸 명령 한 줄만 남고 산출물은 통째로 안 보인다.

어느 하루 실측: 도구 로그는 40개를 아는데 그 시간창에 실제로 바뀐 파일은 143개였다. git 이 단순히 건드린 것(`pull`, `checkout`)을 빼도 **72개가 진짜 작업**이었고, 그중에는 한 프로젝트가 그날 만들어낸 문서 전부가 들어 있었다. 보고서는 그 프로젝트를 "파일 4개" 로 적고 있었다.

그래서 세 번째 소스가 있다 — 그날 이미 활동이 있는 프로젝트만 대상으로 하는 파일시스템 훑기, 별도 필드에. 증거력은 약하다. mtime 은 "바뀌었다" 만 말하지 "누가 왜" 는 말하지 않는다. 그래서 요약기에게 **산출물로 보고하되 만들어진 방식은 단정하지 말라**고 지시한다.

진짜 작업과 git 노이즈를 가르는 데는 주의가 필요하다. `git status --porcelain` 은 **무시된 파일을 나열하지 않으므로**, "status 에 없다" 가 "안 바뀌었다" 를 뜻할 수 없다. 기준은 **추적되면서 깨끗함**이다. 추적 안 되거나 무시된 파일은 git 의 통제 밖이고 그 mtime 은 말 그대로다.

## Codex — `exec` 는 셸 명령이 아니라 JavaScript 를 받는다

Codex 의 `exec` 도구는 셸 명령을 받지 않는다. `tools.exec_command({cmd: "…"})` 를 호출하는 **JavaScript** 를 받고, 한 블록에서 여러 번 호출하며 그 주위를 루프와 부기 코드가 감싼다. 통째로 저장했더니 셸 호출이 수집 바이트의 80% 를 차지했고 단일 항목이 35 KB 에 달했으며, 정작 무엇이 실행됐는지는 그 안에 파묻혔다.

`cmd:` 값만 뽑아낸다. JS 문자열 세 형태를 모두 다뤄야 한다 — `"` 와 `'` 만 지원했더니 명령 지점의 3.7% 가 조용히 사라졌고, 유실분이 **백틱으로 감싼 하위 위임**에 몰려 있었다. 그날 가장 의미 있는 명령들이다.

계획도 같은 방식으로 온다. `tools.update_plan({plan:[{step:…}]})` 이 `exec` 안에서 불리고, **동시에** Codex 는 순수 JSON 인자를 가진 `update_plan` 이라는 `function_call` 을 따로 낸다. 앞의 형태만 처리하면 뒤의 것을 전량 놓친다.

롤아웃이 사람의 세션이 아니라 서브에이전트 스레드일 수도 있고, 그 "사용자 메시지" 는 오케스트레이터의 지시다. 그 필터가 작동하느냐는 세부 하나에 달려 있다 — 서브에이전트 롤아웃은 **끝에 두 번째 `session_meta`** 를 갖는다. 부모의 것이고 source 가 `cli` 다. 마지막 것이 이기게 두면 스레드가 "서브에이전트 아님" 으로 뒤집힌다. 실측 기기에서 다중 meta 파일 136개 중 90개가 그랬고, 그 결과 어느 하루 수집된 프롬프트의 96% 가 기계 대화였다.

## 자격증명 — 세션 로그에 들어 있다

한 달치 프롬프트와 셸 명령을 훑었더니 살아 있는 API 토큰이 평문으로 나왔다. 가정이 아니고 특수한 경우도 아니다. **명령줄에 토큰을 한 번이라도 붙여 넣은 사람은 자기 로그에 그걸 갖고 있다.**

그래서 살균이 두 번 돈다 — 모델이 보기 전의 digest 에, 그리고 게시 전의 완성된 보고서에. 다만 진짜 방어는 구조가 한다. **모델이 쓴 산문만 목적지에 가고 원본 프롬프트와 명령은 절대 가지 않는다.**

패턴에서 두 가지가 중요하다. `\b(API[_-]?KEY|…)` 는 `API_KEY=` 는 잡지만 `OPENAI_API_KEY=` 는 못 잡는다. `_` 가 단어 문자라 키워드 앞에 경계가 없기 때문이고, 실제 `.env` 파일은 거의 전부 접두사가 붙은 이름이다. 그리고 **딕셔너리 키도 데이터를 담는다** — 프로젝트명이 목적지의 속성이 되므로, 값만 훑는 살균기는 그것을 통째로 놓친다.

## 스케줄링 — 제때 시작하는 것과 끝내는 것은 다른 문제다

`launchd` 는 놓친 캘린더 실행을 **정확히 한 번으로 합친다.** 3일 꺼져 있던 기계가 돌아오면 한 번 돈다. 어느 날짜를 썼는지 장부가 없으면 나머지 이틀은 영구히 사라진다. 그래서 자체 장부를 두고 백필한다.

시작만으로는 부족하다. Power Nap 이 켜진 맥은 DarkWake 와 Maintenance Sleep 을 수십 초 단위로 오간다. 정확히 제 시각에 시작한 실행이 수집 도중 얼어붙을 수 있다 — 04:05 에 시작해 13:52 에 끝난 적이 있고 그 사이 대부분은 정지 상태였다. 그래서 작업을 `caffeinate` 로 감싼다. 감싼 명령이 도는 **동안만** 전원 assertion 을 잡고 끝나면 놓는다. 하루 몇 분이지 기계 설정을 영구히 바꾸는 게 아니다.

이 상황에서 워치독은 발동하지 않는다. `signal.alarm` 이 프로세스가 실제로 돌던 시간을 세기 때문이다. 여기서는 그게 옳은 동작이다 — 그냥 잠들었을 뿐인 실행을 중단시키면 이유 없이 그날 보고서를 잃는다.

## 무인 인증 — `USER` 가 필요하다

Claude Code CLI 는 로그인 키체인에서 **계정 이름으로** 자격증명을 찾는다. 환경에 `USER` 가 없으면 로그인돼 있어도 "Not logged in" 이라고 한다.

`launchd` 는 환경변수를 거의 넘기지 않는다 — 실측 기기에서 정확히 하나였다. 그래서 plist 가 `USER` 를 명시하지 않으면 LaunchAgent 는 **매일 밤 여기서 걸린다.** 이 실패는 터미널에서 절대 재현되지 않는다. 셸이 그 값을 넘겨주기 때문이다.

## 목적지 — 날짜 키 upsert, 그런데 그런 기능이 없다

Notion 에는 upsert 도 유니크 제약도 없다. 그래서 날짜 속성에 대해 조회 후 생성-또는-갱신을 한다. 결과가 셋이다.

- **결과가 2건 이상이면 이미 뭔가 잘못된 것이다.** 조용히 하나를 고르면 손상이 누적된다. 작업을 멈추고 그렇게 말한다.
- **페이지 생성은 재시도하면 안 된다.** idempotency key 가 없으므로, 서버에서는 성공했는데 502 로 돌아온 생성을 재시도하면 두 번째 행이 생긴다. 그 뒤로 그 날짜는 영영 쓸 수 없다. 실패하면 다시 조회한 뒤 판단한다.
- **본문은 원자적으로 써야 한다.** 지우고 붙이다 중간에 죽으면 잘린 페이지가 남고, 다음 날 "페이지가 있다" 를 보고 그 손상을 보존한다.

## 보고 — 요약이 거짓말하지 않게 하는 것

보고서는 영구 기록이므로, 지어낸 세부 하나가 **자기 작업에 대한 거짓 기억**이 된다. 생성된 보고서 세 편을 감사한 결과 지어낸 파일 경로도 없었고 없는 프로젝트도 없었지만, 과장은 있었다 — 활동 기록만으로 결과를 단정하거나, 어디에도 맞지 않는 개수를 쓰거나, 시간대 환산을 일관성 없이 적용했다.

그중 둘은 지시가 아니라 **데이터에서** 고쳤다. 그쪽이 훨씬 확실하다.

- 시각은 모델이 보기 전에 현지시간으로 변환한다. 환산할 일이 없으면 일관성 없이 할 수도 없다.
- 잘린 문자열에는 눈에 보이는 표시를 붙이고, 중요한 경우가 들어갈 때까지 잘림 한도를 올렸다. 모델에게 "잘린 문구를 완성하지 마라" 고 타이르는 것보다 애초에 자르지 않는 게 강하다.

나머지는 프롬프트 규칙이다 — 배열에 실제로 있는 것만 세라, 명령이 보여주지 않는 한 산출물의 제작 방식을 쓰지 마라, 수정된 파일을 "한 일" 로는 보되 "끝난 일" 로는 보지 마라, 로그가 가리킬 때만 "다음 할 일" 을 써라.

## 일부러 넣지 않은 것

- **기계가 특정 순간에 깨어 있어야 하는 것.** 이 작업은 돌 수 있을 때 돌고 놓친 것을 채운다.
- **리눅스.** 새 플랫폼은 `platform_support.py` 에 들어간다. `systemd --user` 타이머가 자연스러운 선택일 것이다. 검증 안 된 구현을 내보내는 건 조용히 안 도는 작업을 남에게 쥐여 주는 일이다.
- **두 에이전트 밖에서 한 작업.** 디스크에서 바뀐 파일은 관찰하지만, 작업 보고서는 그 소스만큼만 완전하다.

## 윈도우 이식이 실제로 든 비용

이 문서는 원래 "수집·처리 본체는 이식 가능하고 실행 껍데기만 아니다" 라고 적고 있었다. 진짜 윈도우 기기에서 테스트를 돌려 보니 사실이 아니었다. `platform_support.py` **밖에서** 결함이 일곱 개 나왔고, 그중 가장 나쁜 둘은 눈에 보이지 않는 종류였다.

`project_root()` 는 `/` 로 시작하지 않는 작업 디렉터리를 전부 버렸고, 위로 올라가는 순회는 문자열 `"/"` 에서 멈추도록 돼 있었는데 `D:\` 에서 시작한 경로는 거기에 절대 닿지 않는다. 둘이 합쳐져 기기의 모든 세션이 폐기됐다 — 그리고 **아무것도 실패하지 않았다.** 수집·정제·살균·요약·적재가 전부 정상 종료하면서 "아무 일도 없었다" 고 적었다. 이건 `platform_support.py` 가 막으려던 바로 그 실패 — 조용히 안 도는 작업 — 가 아무도 안 보던 문으로 들어온 것이다.

나머지 다섯. 슬래시로 쓴 제외 목록은 역슬래시 경로에 하나도 안 걸려서 **제외가 통째로 꺼졌다** — 요약기가 자기 자신을 보고하지 못하게 막던 규칙까지 포함해서. `subprocess(text=True)` 는 프로세스 로케일로 디코딩하는데 한국어 설치본에서는 cp949 라서, 한글 커밋 제목 하나가 리더 스레드 안에서 `UnicodeDecodeError` 를 내고 그 저장소를 통째로 날렸다. git 이 돌려주는 슬래시 경로를 윈도우 저장소 경로에 이어 붙이면 `D:\repo\docs/a.md` 가 되는데, `os.walk` 가 내놓는 것과 절대 같지 않다. `os.path.relpath` 는 드라이브가 다르면 값을 돌려주는 대신 예외를 던지는데, 이 도구는 흔히 `D:` 에 있고 홈은 `C:` 에 있다 — 이 결함은 **모델 호출을 이미 지불한 뒤에** 터졌다. 그리고 스케줄러가 ANSI 코드페이지로 연 파일로 리다이렉트한 stdout 은 이 작업이 출력하는 한글을 인코딩하지 못했다.

교훈은 본체가 잘못 짜였다는 게 아니다. **"이식 가능하다" 는 의도에 대한 주장이 아니라 검증에 대한 주장이고, 그걸 하는 유일한 방법은 다른 데서 실제로 돌려 보는 것**이라는 얘기다.
